01

프로젝트 개요

CI/CD 파이프라인이 성공했다고 해서 배포가 끝난 것은 아니라고 보고, 새 버전의 실제 트래픽과 상태까지 확인하는 운영 흐름을 만들었다.

환자, 처방, 예약, 알림 4개 서비스를 대상으로 CI/CD를 구성하고, 심화 단계에서 Istio Service Mesh를 적용해 Canary와 Blue/Green 배포를 검증했다. 팀장과 Observability 담당으로서 트래픽, 오류율, 응답시간, Envoy 리소스 상태를 Prometheus/Grafana/Kiali로 확인할 수 있도록 관찰 기준을 정리했다.

PROJECT GOAL배포 이후까지 확인하는 Delivery Flow

Build → Deploy → Traffic Shift → Observe를 하나의 절차로 연결했다.

MY ROLE팀장 · Observability

전체 단계의 연결과 배포 후 검증 지표를 담당했다.

DEPLOY STRATEGYCanary · Blue/Green

서비스 특성에 따라 두 가지 전환 방식을 나눠 적용했다.

KEY SIGNALSTraffic · Error · Latency · Resource

트래픽 전환 후 서비스 상태가 악화되는지 확인할 기준을 잡았다.

02

문제 정의

PROBLEM 01배포 성공과 서비스 정상은 다름

ArgoCD Sync가 성공해도 실제 요청이 새 버전에 정상적으로 도달하는지 별도 확인이 필요했다.

PROBLEM 02한 번에 전환하면 장애 영향이 큼

새 버전 전체 전환은 오류가 있을 때 사용자 영향 범위가 커질 수 있다.

PROBLEM 03운영 판단 기준이 부족

다음 Canary 단계로 진행할지 결정하려면 트래픽, 에러, 응답시간을 함께 볼 수 있어야 했다.

03

AS-IS → TO-BE

AS-IS

  • 배포 파이프라인 성공 여부 중심 확인
  • 새 버전 전체 전환 시 장애 영향 범위가 큼
  • 서비스 간 호출 흐름을 개별 로그로 확인
  • 배포 전후 지표 비교 기준이 분산됨
→

TO-BE

  • GitOps 배포 후 Istio로 단계적 Traffic Shift
  • Canary 단계별 상태 확인 후 다음 비율로 전환
  • Kiali에서 Service Topology와 버전별 흐름 확인
  • Prometheus/Grafana 지표를 공통 판단 기준으로 사용

07

관찰 기준

TRAFFICRequest / Routing 비율

Canary 비율이 의도한 대로 적용되고 있는지 확인한다.

ERRORHTTP Error Rate

LATENCYResponse Time

버전 변경으로 응답시간이 악화되는지 비교한다.

RESOURCEEnvoy CPU / Memory

Sidecar 적용 후 Proxy 리소스 사용량을 함께 관찰한다.

08

결과와 배운 점

4개 서비스의 배포 자동화, 트래픽 전환, 상태 확인을 하나의 운영 시나리오로 연결했다.

성과 수치를 임의로 만들기보다, 실제로 검증한 서비스 수와 Canary 단계, 관찰 기준을 중심으로 결과를 제시했다. 이 과정에서 "배포 완료"가 아니라 "새 버전이 정상적으로 트래픽을 처리하는지"까지 확인해야 운영이 끝난다는 관점을 정리했다.
