01

프로젝트 개요

애플리케이션 팀이 각자의 코드를 개발하더라도, 빌드 이후 배포 과정은 동일한 규칙으로 흘러가도록 만드는 것이 목표였다.

Frontend, Backend, AI가 서로 다른 저장소에서 개발되는 환경에서 CI 결과물인 Container Image를 ECR에 저장하고, GitOps 저장소의 배포 상태를 변경한 뒤 ArgoCD가 EKS에 반영하도록 구조를 설계했다. 서비스 코드와 배포 설정의 책임을 분리하고, dev/prod 환경이 늘어나도 YAML을 반복 복사하지 않는 구조에 초점을 맞췄다.

PROJECT GOAL반복 가능한 배포 구조

서비스마다 별도의 배포 방식을 만들지 않고 공통 규칙으로 배포한다.

MY FOCUSBuild 이후부터 Cluster 반영까지

CI, Image Registry, Helm, GitOps, ArgoCD 사이의 연결을 담당했다.

COLLABORATION서비스 팀과 배포 인터페이스 정의

애플리케이션 코드와 배포 설정의 소유 영역을 나눴다.

KEY OUTPUT공통 Chart + 환경별 Values + ApplicationSet

서비스/환경이 늘어날 때 변경 범위를 최소화하는 구조를 만들었다.

02

문제 정의

PROBLEM 01서비스별 YAML 중복

Deployment와 Service를 서비스마다 복제하면 공통 변경 시 수정 지점이 늘어나고 설정 차이가 생기기 쉽다.

PROBLEM 02환경별 설정 혼재

dev/prod의 도메인, 리소스, 이미지 태그 차이를 한 파일에서 관리하면 운영 환경 변경 범위가 불명확해진다.

PROBLEM 03배포 책임 경계 불명확

서비스 저장소가 Kubernetes 설정까지 모두 가지면 개발 코드와 운영 상태 변경이 섞이고 협업 시 소유권이 모호해진다.

03

구축 방향

신규 구축 프로젝트이므로 기존 구조를 억지로 비교하기보다, 서비스와 환경이 늘어날 때 유지보수 가능한 배포 구조를 만드는 데 초점을 맞췄다.

STANDARDIZE공통 Workload 구조

Deployment와 Service의 공통 부분은 Helm Chart로 묶고 서비스별 차이만 Values로 전달한다.

SEPARATE ENVdev / prod 설정 분리

도메인, 리소스, Image Tag, Secret 참조처럼 환경에 따라 달라지는 값을 명시적으로 분리한다.

SEPARATE RESPONSIBILITYApplication과 배포 상태 분리

서비스 코드는 각 팀 Repository에서, Kubernetes 배포 상태는 GitOps Repository에서 관리한다.

TRACEABILITYCommit과 배포 버전 연결

Commit SHA 기반 Image Tag와 GitOps 변경 이력을 통해 어떤 코드가 배포되었는지 추적할 수 있게 한다.

04

담당 역할과 기여

CIJenkins 기반 Build/Test/Image Push 흐름

서비스 변경을 감지해 Container Image를 생성하고 ECR에 Push하는 흐름을 기준으로 설계했다.

KUBERNETES공통 Deployment/Service 템플릿

서비스별 차이를 Values로 주입하도록 Helm Chart 구조를 정리했다.

GITOPS배포 상태 전용 Repository 구조

charts, environments, argocd, platform 영역을 분리해 역할과 변경 범위를 명확히 했다.

ARGOCDApplicationSet 기반 배포 생성

서비스와 환경이 늘어날 때 Application YAML을 반복 작성하지 않도록 구성했다.

VERSIONINGCommit SHA 기반 Image Tag

CI 결과와 GitOps 상태를 같은 버전 기준으로 연결해 배포 추적성을 높였다.

COLLAB팀 간 전달 항목 정의

서비스 팀이 제공해야 할 포트, Health Check, 환경 변수, Image 정보와 Infra/GitOps 측 책임을 구분했다.

06

설계 판단

DECISION 01Application Repo와 GitOps Repo 분리

애플리케이션 변경과 운영 상태 변경의 리뷰 범위를 분리하고, ArgoCD가 GitOps 저장소를 단일 배포 소스로 보게 했다.

DECISION 02서비스별 Chart 대신 공통 Chart

현재 서비스의 Workload 구조가 유사하므로 중복 Chart보다 하나의 공통 Chart와 Values 차이가 관리 비용이 낮다고 판단했다.

DECISION 03Application 대신 ApplicationSet

서비스 × 환경 조합이 증가할 것을 고려해 개별 Application 생성보다 선언 규칙을 반복 사용하는 방식을 선택했다.

DECISION 04dev / prod Values 분리

운영 리소스, 도메인, Secret 참조와 같은 환경 차이를 명시적으로 분리해 배포 사고 가능성을 줄이는 방향으로 구성했다.
